# P06. SCD2 на dim_product

## Что сделано

Для справочника `dim_product` реализован SCD2 — версионирование строк.
Добавлены три служебных поля:

- `valid_from` — дата, с которой версия действует;
- `valid_to`   — дата, по которую (для текущей — 9999-12-31);
- `is_current` — TRUE только для актуальной версии.

Для текущей версии используется `valid_to = 9999-12-31` вместо `NULL`:
это стандартный приём SCD2, при котором диапазонное условие
`valid_from <= d < valid_to` работает без отдельной обработки NULL.
Если бы `valid_to` был NULL, сравнение `d < NULL` возвращало бы NULL,
и запись не находилась бы — пришлось бы писать `valid_to IS NULL OR valid_to > d`.

## Демонстрация смены атрибута

Товар `product_id = 1`:

1. Первая версия: `category = Серьги`, `valid_from = 2020-01-01`, `valid_to = 9999-12-31`, `is_current = true`.
2. Смена: `UPDATE` закрывает первую версию — `valid_to = 2024-02-01`, `is_current = false`.
3. `INSERT` добавляет новую — `category = Пирсинг`, `valid_from = 2024-02-01`, `is_current = true`.

Сценарий правдоподобный: серьги для пирсинга переклассифицировали
в отдельную категорию `Пирсинг`.

Запрос `SELECT ... WHERE product_id = 1` показывает две версии.
Результат сохранён в `scd2_output.txt` (всего 6 версий для 5 товаров).

## Как факт попадает в нужную версию

Для продажи с датой `sale_date` берётся та версия справочника, где:

    valid_from <= sale_date < valid_to

Это классическое соединение факта со SCD2-измерением. В реальной загрузке
это делается в ETL. Здесь — упрощённо, но правило явное: январские продажи
соединятся со старой версией (`Серьги`), февральские — с новой (`Пирсинг`).

## Почему это важно

Без SCD2 при смене категории старые продажи в отчётах «по категориям»
внезапно окажутся в новой категории. Отчёты за прошлые периоды начнут врать.
SCD2 фиксирует версию на момент события.
