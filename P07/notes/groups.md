# Логические группы таблиц и ключи дедупликации

## Зачем группировать

При инкрементальной загрузке нельзя перепроверять все 13 таблиц на дубли.
Это медленно: каждая проверка — это JOIN или сравнение сотен тысяч строк.

Вместо этого таблицы разбиты на 4 логические группы по бизнес-смыслу.
При загрузке новой партии обновляется **только та группа, в которую пришли данные**.

## Группы

| Таблица | Ключ дедупликации |

| dim_customer | customer_id |
| dim_date | date_id |

**Когда грузить:** пришла партия `fact_sales.csv` или обновились справочники товаров/магазинов/клиентов.

## Индексация (ключ дедупликации)

В ClickHouse роль индекса играет `ORDER BY` в движке MergeTree-семейства.
Для `ReplacingMergeTree` `ORDER BY` — это **ключ, по которому строки дедуплицируются** при мерже.

Ключ выбран как первичный идентификатор каждой таблицы:
- для фактов — id события (sale_id, visit_id, ...);
- для справочников — id сущности (store_id, product_id, ...).

Такой ключ:
- уникален по смыслу (одна строка = одна сущность / одно событие);
- используется в JOIN'ах;
- позволяет ClickHouse отсекать ненужные блоки при фильтрации.

## Что это даёт

- **Нет TRUNCATE.** Данные только добавляются.
- **Дедупликация автоматическая.** `ReplacingMergeTree` при мерже оставляет одну версию строки на ключ.
- **Экономия проверок.** Грузим группу — не трогаем остальные.
- **Проверка через FINAL.** `SELECT count(*) ... FINAL` возвращает число уникальных строк.
