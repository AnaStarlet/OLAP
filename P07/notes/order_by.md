# Обоснование ORDER BY в ClickHouse

## Что такое ORDER BY в ClickHouse

`ORDER BY` в MergeTree-семействе — это не уникальный ключ, как `PRIMARY KEY` в Postgres.
Это порядок, в котором строки физически лежат на диске. По нему ClickHouse
решает, какие блоки читать при фильтрации.

В движке **`ReplacingMergeTree`** `ORDER BY` играет **вторую роль**: это ключ дедупликации.
При мерже строки с одинаковым ключом схлопываются — остаётся одна, самая новая.

## Ограничение: только не-Nullable колонки

ClickHouse запрещает Nullable-колонки в `ORDER BY` (ошибка `Sorting key
contains nullable columns`). Поэтому в качестве ключа дедупликации взяты
только не-Nullable первичные id:

- у справочников — id сущности (`store_id`, `product_id`, `customer_id`, ...);
- у фактов — id события (`sale_id`, `visit_id`, `interest_id`, ...).

## Почему именно эти колонки

1. **Уникальность по смыслу.** Одна строка = одна сущность / одно событие.
   Значит id идеально подходит на роль ключа дедупликации.
2. **Используются в JOIN'ах.** По id соединяем факты со справочниками.
   Если данные лежат рядом по ключу — JOIN идёт быстрее.
3. **Не-Nullable.** ClickHouse требует этого для ключа сортировки.

## Как работает дедупликация

При вставке строки с уже существующим ключом:
- ClickHouse записывает её в новый кусок (part);
- при фоновом мерже куски сливаются;
- строки с одинаковым ключом заменяются одной, самой новой.

Чтобы получить актуальный результат сразу, используют `FINAL`:

    SELECT count(*) FROM olap.fact_sales FINAL;

## Что это даёт

- Загрузка идёт **инкрементально**, без `TRUNCATE`.
- Дубли удаляются **автоматически** — по ключу дедупликации.
- Никаких ручных проверок «есть ли уже такая строка» — движок делает это сам.
